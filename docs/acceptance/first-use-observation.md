# 首次使用平台的 QA 演练观察表

## 使用时机

在小规模真实批次验收当天执行。对象是具备 QA 背景、但第一次使用本平台的人，不是 QA 新人，也不是需要学习测试基础的人。

目标不是考参与者会不会测试，也不是验证测试基础教学是否充分，而是验证平台是否能让具备 QA 背景的人在没有平台操作讲解的情况下，第一次使用时也清楚知道下一步该干嘛。

## 演练前准备

- 当前分支：`feat/qa-platform-ux-modernization`
- 工作区干净。
- 已完成 `uv run python scripts/ux_acceptance_preflight.py`。
- 准备好 [ux-small-batch-prd.md](./ux-small-batch-prd.md)。
- 主持人不要提前演示页面。
- 主持人不要解释“知识库”“工作台”“用例资产”“落库归档”等平台术语。
- 主持人不要告诉参与者按钮、菜单、路径或页面层级。
- 主持人可以说明这是一套测试用例生成平台，不评价参与者个人能力。

## 给参与者的唯一任务

把下面这段话直接发给或读给参与者：

```text
请把这份 PRD 上传到平台，生成测试用例，找到需要审查的批次，抽查几条用例，然后找到导出结果的地方。
```

如果真实批次已经由你提前跑完，可以改成：

```text
请找到这个系统里刚生成的测试用例批次，抽查几条用例，然后找到导出结果的地方。
```

## 观察规则

- 先观察，不马上提示。
- 参与者问“这是什么意思”时，先记录原话。
- 参与者问“下一步点哪里”时，先记录，再给最小提示。
- 最小提示只能是目标级提示，不说具体按钮、菜单、路径或术语定义。例如“你现在需要找到这个系统的资料入口”，不要说“点项目/系统”。
- 如果必须给出操作级提示才能继续，例如“点项目/系统”“点生成用例”“去导出中心”，该步骤不能记为独立完成，并且上传、生成、审查、导出主链路中的操作级提示至少按 P1 记录。
- 不把业务 PRD 理解困难直接判为 UI/UX 问题；只有页面没有给出足够线索时才算 UI/UX 卡点。
- 不要求参与者完成删除、落库归档等破坏性动作；能找到入口并理解含义即可。

## 判级规则

| 判级 | 标准 | 例子 |
|---|---|---|
| P0 | 主流程无法继续，或用户无法完成上传、生成、审查、导出中的关键一步 | 上传后文档类型错误导致无法判断资料；生成入口不可见；批次页打不开；导出入口不存在 |
| P1 | 主流程能继续，但没有提示就不知道下一步，或页面状态明显误导 | 生成后不知道去哪里看进度；待澄清/失败/待审核状态无法区分；误以为不用审查就能归档 |
| P2 | 能完成，但效率低、文案弱、布局拥挤或需要多余点击 | 入口命名略绕；筛选项不好找；空态说明不够直接 |
| 非 UI 问题 | 参与者不理解业务 PRD、测试策略或公司流程，但页面线索足够 | 不知道某业务字段含义；不知道应该覆盖哪些测试维度 |

## 通过标准

可以进入 PR / 合 main 准备的最低标准：

- 无 P0。
- 无 P1，或 P1 已有明确修复任务且不影响上传、生成、审查、导出主链路。
- P2 可以记录为后续优化。
- 不需要平台操作讲解；如有提示，只能是目标级提示。
- 参与者最终能说清楚：资料从哪里上传、生成在哪里看进度、用例在哪里审查、资产和导出在哪里。

## 观察者自检

- 我有没有提前解释按钮位置？
- 我有没有把操作级提示误记成独立完成？
- 我有没有把业务理解困难误判为 UI 问题？
- 我有没有记录参与者原话，而不是只写自己的解释？
- 我有没有区分“找不到入口”和“找得到但效率低”？
