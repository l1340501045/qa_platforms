## 1. 原始需求

> 初步是想达成知识库搭建并且支持了 RAG 检索或者 Agent Skills 检索，然后 AI 生成用例的效果能等同于资深测试开发工程师写的用例。

---

## 2. 发散想法

### 功能方向

| 编号 | 想法 | 一句话描述 | 值得深入？ |
| :--- | :--- | :--- | :--- |
| F1 | 知识库搭建与组织 | 按系统维度组织文件夹结构，支持导入 md+图片文件夹，系统下含需求文档、技术文档、测试用例、漏测 Bug | ⭐ |
| F2 | 智能检索与关联 | Agent Skills/RAG 检索；文档间自动关联（需求↔技术文档↔用例↔漏测 Bug）；可交互原型链接辅助理解 | ⭐ |
| F3 | AI 用例生成引擎 | 点击需求文档触发生成；综合技术文档、规则库、历史用例、漏测 Bug、原型链接；Playwright 辅助探索 | ⭐ |
| F4 | 用例质量保障 | 每条用例标注原文出处/可追溯性；不确定用例标注可信度；原型交互来源标注风险 | ⭐ |
| F5 | 人工 review + AI 迭代 | AI 生成 → 人工 review（标注不确定项）→ 反馈/修改 → AI 迭代优化 → 落库 | ⭐ |
| F6 | 版本管理 | 需求文档和测试用例均有版本管理（类 git diff）；迭代需求时 AI 自动维护老用例 | ⭐ |
| F7 | 导出功能 | 支持导出，格式规范由用户后续提供 | — |

### 用户场景

- **场景 1**：QA 工程师 在拿到新需求时 想要 把 PRD 文件夹上传到平台对应系统 以便 AI 能基于完整上下文生成高质量用例
- **场景 2**：QA 工程师 在生成用例后 想要 review 并标注不确定项 以便 AI 迭代优化后落库为正式用例
- **场景 3**：QA 工程师 在迭代需求变更时 想要 AI 自动识别影响范围并更新老用例 以便 保持用例与需求的一致性

### 参考案例

| 产品/功能 | 可借鉴的点 | 与我们的差异 |
| :--- | :--- | :--- |
| 可交互原型（AI 生成） | 产品提供可操作原型链接，AI 可通过 Playwright 探索辅助理解需求 | 原型可能有交互 bug，需标注风险 |
| Git 版本管理 | 文件变更追踪、diff 对比 | 应用到需求文档和测试用例的版本管理 |

### 技术可能性

- Agent Skills（动态推理）vs RAG（静态检索）：需评估哪种方案更能理解业务上下文和跨系统关系
- Playwright MCP：可用于探索可交互原型，但原型本身质量不可控，需降级处理
- 版本管理：需求文档和用例的变更追踪可参考 git 模型，但粒度和展示方式需设计

### 开放问题

- Agent Skills vs RAG 的落地策略如何评估？二者是否可以混合使用？
- 可交互原型链接的可靠性如何量化？AI 从不可靠源头获取的信息如何标注风险？
- 导出格式规范待用户后续提供
- "跨系统影响"的自动关联如何实现？系统间关系如何建模？
