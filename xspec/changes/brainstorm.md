### 用户场景

- **场景 1**：QA 工程师 在上传 PRD 并触发生成后 想要 收到通知并快速进入用例库查看全貌 以便 确认生成质量
- **场景 2**：QA 工程师 在需求变更时 想要 重新生成用例并看到与上一版的差异/演化原因 以便 判断哪些用例需要更新
- **场景 3**：QA 工程师 在日常工作中 想要 按功能模块维度查看所有用例覆盖情况 以便 发现测试盲区
- **场景 4**：QA 工程师 在用例确认后 想要 一键导出当前系统/批次的用例 以便 在测试执行中使用

### 参考案例

| 产品/功能 | 可借鉴的点 | 与我们的差异 |
| :--- | :--- | :--- |
| TestRail | Suite → Section → Case 的三级树形结构 | 我们的 Section 来自 AI 自动归类而非手建 |

### 技术可能性

- 树形结构的"功能模块"层可复用 parse 阶段已聚合的 provenance.source_section / derived_from，无需新建 AI 归类步骤
- 用例版本化可对齐复用现有 quality_flywheel 表（已有 modification_reason/modification_type 字段）
- 流水线可观测性可直接消费现有 stage_artifacts 表（已存 status/duration_ms/open_questions）
- 全局搜索中文分词需选型：pg_trgm / ILIKE / 或后续引入 pg_jieba

- 用例身份锚点的具体逻辑键设计（system + feature + dimension + test_point_description 指纹）— **已定稿：确定性键锚定测试点意图而非标题**

## 3. 初步聚焦

### 推荐深入的方向

1. **全量落地（用户选定）**：① + ② + ③ + ④ + ⑤ + ⑥ + ⑦ + ⑧ + ⑨ 全部纳入，分两段交付
2. **第一段优先**：信息架构 + 树形用例库（批次快照过渡）+ 详情面板 + 通知 + 面包屑 + 可观测性 + 导出优化
3. **第二段跟进**：单条用例级血缘 + 演化原因 + 混合锚点 + iteration_service 改造 + review 状态继承

### 建议排除的方向

- **多人实时协作编辑**：初期单人使用，数据模型预留 actor/author 即可
- **Playwright 自动化脚本生成动线**：本次不做，但用例详情面板保证结构化步骤和稳定 ID 为将来留锚点
