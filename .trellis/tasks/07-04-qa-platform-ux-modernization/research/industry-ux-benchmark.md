# QA 平台 UI/UX 行业基准调研

## 结论

### 1. 企业后台先解决任务流，不先追求“漂亮”

Nielsen Norman Group 的启发式原则强调：系统状态可见、语言贴合用户真实世界、用户可控、识别优先于记忆、错误预防、审美与极简。这些原则映射到 QA 平台上，就是：

- QA 不应该猜当前批次是否在跑、是否失败、下一步该做什么。
- 页面不应该暴露太多内部工程词，应该围绕“上传资料、生成用例、处理澄清、审查、导出”组织。
- 树、筛选、状态、用例详情要让用户识别和选择，而不是记住某个路径在哪里。

### 2. 树形导航不能默认制造信息噪声

WAI-ARIA Tree View Pattern 把树视为一种可聚焦、可展开/收起、可键盘操作的层级控件。Ant Design Tree 也提供受控展开、搜索、虚拟滚动/height 等能力。对于当前 433+ 用例、上百模块/分支的场景，默认全展开违反了“降低认知负担”的方向。

本项目应采用：

- 默认展开 root + 文档 + 重要模块，不默认全展开。
- 明确的展开/收起全部按钮。
- 搜索/过滤节点。
- 树容器固定高度，内部滚动或虚拟滚动。
- 选中节点后右侧内容稳定，不让页面整体被树高度撑开。

### 3. 数据密集页面应以筛选、表格、状态和批量操作为中心

Ant Design Table 面向数据展示、排序、筛选、分页、固定列/滚动等企业后台场景。QA 平台的用例库、审核中心和导出中心都属于数据密集页面，最佳方向是：

- 表格密度适中，关键列固定或限制宽度。
- 筛选条紧贴数据表。
- 状态标签颜色稳定且语义统一。
- 分页/虚拟滚动避免一次性渲染过多数据。
- 详情放在 Drawer，不打断列表上下文。

### 4. 测试管理的核心是可追溯资产

ISO/IEC/IEEE 29119 是软件测试过程标准族，虽然具体 UI 不由该标准规定，但它提醒测试管理工具的核心是测试工作产品、过程、记录和可追溯性。映射到本平台：

- 文档类型不能丢失；PRD、技术文档、测试规则、原型的语义不同。
- 系统、文档、批次、测试点、用例、审查状态、导出之间要保持清晰关联。
- 用例库不只是列表，应支持按模块、分支、质量桶、优先级、审核状态组织和追踪。

### 5. 本项目对齐建议

必须优先做：

- 修复系统统计真实数据展示。
- 上传前选择 `doc_type`，不要默认一切都是 `other`。
- 树默认折叠、搜索、固定高度、内部滚动。
- 用例树支持模块下递归分支，不强行平铺。
- 统一工作台/用例库共享组件，减少两份实现漂移。
- 保留主流程状态提示和错误恢复入口。

暂不优先做：

- 大量装饰图形、营销式首页、复杂动效。
- 引入全新 UI 框架。
- 移动端优先。
- AI 自动猜文档类型并静默应用；可作为后续辅助，但第一版应让用户显式选择。

## 对当前截图问题的判断

- 系统列表 0/0：不符合状态可见性和数据可信原则。实际 DB 有 1 个文档、3 个批次，应由后端返回准确聚合。
- 上传后 `other`：不符合错误预防。用户在上传前没有机会声明类型，系统默认造成资产语义丢失。
- 默认全展开树：不符合复杂层级导航可用性。当前树应改为受控展开、搜索、滚动和递归层级。

## 自审

这些资料主要覆盖通用企业后台、可访问性和测试管理原则，不是某个竞品 UI 的完整复制。当前项目更需要“以 QA 任务流组织复杂资产”的架构修正，而不是单纯换皮。因此 PRD/设计把数据契约、树模型、共享组件和分支治理放在视觉 polish 前面。
