# Testcase Oracle Guard Alignment

## Goal

让 testcase_generator 的可执行用例主集只包含有可靠测试依据、可判定且不与 PRD 冲突的断言；把证据不足、需求待确认、PRD 内部冲突、外部目录缺失和无技术方案支撑的技术实现假设分流到 `needs_spec` / clarification / conflict 类资产中。

本任务不是继续优化 `.audit` 模块树分类。模块树已基本可用，本任务聚焦生成、验证、收敛和导出分流里的 oracle 质量闸。

## Background

最新审查包：

- `.audit/0627a024-6d63-4d9c-a0a6-0f58dc9af0b5`
- active cases: 2522
- duplicate cases: 204
- verdict: `grounded=2112`, `ungrounded=307`, `undefined=78`, `conflict=25`
- unresolved module: 54

审查发现的问题集中在用例内容质量，不是单纯的分类规则：

- `【需求待确认】` 类用例进入可执行主集。
- PRD 只给字段约束时，用例生成了具体 toast、HTTP 状态码、接口 payload、落库表名、worker、cron、轮询频率等未定义 oracle。
- 没有技术方案时，生成了接口契约、幂等、异步任务、重试、状态码、表结构等技术实现断言。
- PRD 内部存在冲突时，用例仍可能进入 `main`，而不是标为 `conflict` 或 `needs_spec`。
- UI 图述、原型、AI caption 被当作高置信事实来源，推出了具体布局、文案或交互细节。
- “等”“见外部目录”被当成完整映射表，生成了唯一具体映射断言。
- 字数/边界推理不稳，例如 9 个半角字符应按 4.5 向上取整为 5，不应判非法。

## Requirements

### R1. 澄清项分流

标题、步骤、预期或验证理由中包含 `需求待确认`、`待确认`、`PRD未定义`、`无确定断言` 等信号的内容，不得作为可执行主集用例导出。

这些内容应保留为 `needs_spec` / clarification / debt，而不是直接删除。

### R2. Fake Oracle Guard

如果 PRD 只声明约束或业务规则，没有明确具体提示文案、HTTP 状态码、接口 payload、表名、worker、cron、轮询频率、精确布局等 oracle，则生成或验证阶段不能把这些具体断言标为 `grounded/main`。

允许保留业务级预期，例如“应阻断提交”“应校验失败”“应提示错误”，但不允许编造具体文案或实现细节。

### R3. 无技术方案时禁写技术派生实现断言

没有技术方案或明确接口契约章节时，不得将以下内容作为确定可执行断言：

- `api_contract`
- HTTP 状态码和响应结构
- 数据库表名、落库字段、事务细节
- worker / MQ / cron / 轮询频率
- 重试次数、幂等实现、并发锁实现

不得误伤 PRD 明确写出的业务级权限、安全、状态、边界、异常场景。

### R4. PRD 冲突分流

当 verify 阶段识别 `cross_section_conflict=True` 且 `conflicting_refs` 非空时，该用例不得静默留在 `main`。

应分流为 `conflict` / `needs_spec` / `needs_pm` 等待裁决资产，并保留冲突证据坐标。

### R5. 低信任证据降权

UI 图述、原型、AI caption 只能辅助理解。除非 PRD 正文、高信任 source 或明确 UI 规格写出，否则不能单独支撑具体文案、精确布局、接口细节或状态码断言。

当低信任来源与 PRD 正文冲突时，以 PRD 正文为准；无法判断时进入 `needs_spec` 或 `conflict`。

### R6. 外部目录和“等”防误判

遇到“等”“见外部目录”“参考第三方目录”但本地证据没有完整映射表时，不得生成唯一具体映射断言。

典型例子：不能仅凭“见巨量事件目录”断言某优化目标必然映射 `active_pay`。

### R7. 字数和边界确定性校验

对已定义的字数/边界规则使用确定性逻辑或测试覆盖，不依赖模型自由推理。

必须覆盖半角/全角换算例子：9 个半角字符 = 4.5，按规则向上取整为 5。

### R8. 指标不能靠改标签美化

修复应提升主集可执行性和 clarification/debt 的可审查性。不得通过把不确定项直接删掉、全部标 `grounded`、或仅调整 `.audit` 分类来让指标变好。

### R9. Guard 规则必须区分通用质量闸与领域规则

`guards.py` 中不得长期堆积只适用于单一 PRD / 单一业务域的硬编码规则。

当前批创系统里的 `投放链接`、`监测链接`、`标题包`、`素材评估`、`任务状态`、`宏参数` 等规则可以先作为本批次质量修复的领域规则使用，但必须被标记为领域规则，不得伪装成所有 PRD 都适用的通用 guard。

后续如果接入电商、CRM、财务等不同 PRD，通用 guard 应继续有效，领域规则必须来自可替换的 PRD facts / domain rule pack，而不是继续往通用 guard 文件里追加 if/regex。

通用 guard 至少包括：

- 证据不足的具体 oracle 分流。
- 纯模糊预期分流。
- 技术派生断言无技术方案分流。
- 数字、状态名、字段约束等事实是否有证据支撑。
- 跨实体、跨层级 conflict 降级为 `verify_uncertain`。

领域规则至少包括：

- 特定业务实体边界，例如批创里的投放链接 vs 监测链接。
- 特定模块状态口径，例如任务中心展示状态 vs 底层业务状态机。
- 特定业务事实和主链路，例如标题包、素材评估、宏参数、批创提交链路。

## Out Of Scope

- 不跑完整真实批次。
- 不重构整个 pipeline。
- 不继续大范围调整模块树分类规则。
- 不新增 DB / API 层能力。
- 不解决 PRD 本身冲突，只负责暴露和分流。
- 不在本任务内一次性完成多行业领域包系统，但必须记录拆分方向，避免当前硬编码继续扩散。

## Acceptance Criteria

- [ ] 每个 guard 至少有一个失败优先的单测，修复后通过。
- [ ] `【需求待确认】` 类内容不进入可执行主集，并保留在 clarification/debt 类资产。
- [ ] 无 PRD 证据的具体 toast、状态码、payload、表名、worker、cron、轮询频率断言不会被标为 `grounded/main`。
- [ ] 无技术方案时，技术派生维度不会被误放行；PRD 明确业务规则不被误杀。
- [ ] `cross_section_conflict=True` 且有冲突 refs 的用例会被分流，并保留证据。
- [ ] 低信任 source 不能单独支撑高精度 oracle。
- [ ] 外部目录不完整时，不生成唯一具体映射断言。
- [ ] 字数边界规则有确定性测试覆盖。
- [ ] 新增/修改 guard 时能说明它属于通用 guard 还是批创领域规则；领域规则不得被描述为跨行业通用规则。
- [ ] 验证命令通过：`uv run ruff check`、`uv run ruff format --check`、相关 pytest。

## Critical Self-Review

这套任务有三个容易做错的地方：

1. 不能把所有 `undefined` 或 `ungrounded` 直接删除。它们经常是有效风险，应分流为澄清或产品裁决。
2. 不能因为“没有技术方案”就删除所有异常、权限、安全或状态用例。PRD 明确写出的业务规则仍然是合法测试依据。
3. 不能只修导出包分类。真正的问题在生成、验证、收敛或导出分流链路中 oracle 证据不足，必须有测试证明主集行为改变。
4. 不能把当前批创 PRD 的补丁持续堆进通用 guard。短期可以先修真实批次，长期必须把通用质量闸、PRD facts、领域规则包拆开，否则换成电商/CRM PRD 会误杀或漏放。
