# 首次使用平台 QA 演练观察表

## 目标

把“具备 QA 背景但首次使用本平台的人”的任务演练整理成可执行观察表，明确记录项、P0/P1/P2 判级和回填方式。

## 背景

当前 `docs/acceptance/runbook.md` 已经描述了首次使用平台演练，但内容仍偏摘要。周一真实验收时，如果只靠口头观察，容易漏掉：

- 参与者在哪一步第一次迷路。
- 是否是页面没有线索，还是参与者不熟悉业务资料。
- 是否需要口头提示，提示了几次。
- 卡点应该判 P0、P1 还是 P2。
- 是否可以作为 UI/UX 合 main 的证据。

## 要求

- 新增 `docs/acceptance/first-use-observation.md`。
- 明确演练前准备、主持人话术、禁止提前解释的内容。
- 明确任务成功路径：进入系统、上传 PRD、触发生成、理解批次状态、找到审查页、抽查用例、找到导出。
- 提供逐步观察表，记录是否独立完成、耗时、提示次数、卡点和判级。
- 明确 P0/P1/P2 判定标准，尤其区分“主流程断”和“效率/文案问题”。
- 更新 `docs/acceptance/runbook.md` 和 `docs/acceptance/README.md` 链接观察表。
- 更新跑批后回填模板，让用户可以直接引用观察表结果。
- 补充 `review.md`，批判性说明观察表能证明什么、不能证明什么。

## 不做

- 不改产品代码。
- 不触发真实 LLM 生成。
- 不替代真实批次跑批和 `.audit` 审查。
- 不要求参与者是 QA 新人；对象是具备 QA 背景但首次使用本平台的人。

## 验收标准

- `docs/acceptance/first-use-observation.md` 自包含，可直接拿来执行演练。
- runbook 和 README 能指向观察表。
- 回填模板能接收观察表结论。
- 观察表不把“参与者不懂业务 PRD 内容”误判为 UI/UX 失败。
- `review.md` 明确：观察表只是证据采集工具，不是已经完成真人演练。
