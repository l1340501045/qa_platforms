## 用例质量判断

总体质量是“可进入 QA 审查”，不是“可直接交付”。

数据库核对：

| 指标 | 数值 |
|---|---:|
| 总用例 | 2660 |
| 主集 grounded | 1969 |
| needs_spec | 632 |
| to_fix | 59 |
| duplicate_of 非空 | 175 |
| 单步骤用例 | 971 |
| review_status=pending | 2660 |

关键判断：

- `main + grounded = 1969`，说明已经有一批可作为候选主集的用例。
- `needs_spec + to_fix = 691`，占总量约 26.0%，不应直接交付给 QA 当完成资产。
- `review_status` 全部仍是 `pending`，说明业务上还未完成 QA 人工审查/归档。
- 单步骤用例不是天然问题。抽样发现部分一步用例可执行，例如“授权成功对话框标题/描述验证”“任务数据权限：管理员可查看全量任务”。但也有 `TP-xxx 页面元素核对（unresolved）` 这类标题过泛，应该继续压缩或归为审查债务。

典型问题样本：

1. **规格缺失却产成确定标题**
   - 标题：`【需求待确认】批量添加200组×30条素材（6000条）后弹窗渲染和操作响应时间不超过3秒`
   - 问题：标题隐含 3 秒 SLA，但预期又说 PRD 未定义该行为。
   - 根因：探索性问题/性能假设没有和可执行用例分流。

2. **PRD 未定义的技术契约被写成用例**
   - 标题：`批量修改投放人提交调用POST /api/accounts/bulk-assign，请求体包含ids和ownerName`
   - 问题：PRD 未定义接口路径和请求体字段。
   - 根因：缺少技术方案时，生成侧仍把推测接口当成断言。

3. **跨章节冲突进入 to_fix**
   - 标题：`标题列表-投放组长角色可看到本组所有成员创建的标题包`
   - 问题：部分条款支持、部分条款冲突，需产品裁决。
   - 根因：PRD 本身存在角色权限口径冲突，生成侧已经识别，但 UI/流程应把它作为待处理债务，而非静默混在主集。

4. **状态枚举写错**
   - 标题：`所有子项成功且无失败/取消项时任务状态变为'提交完成（全部成功）'`
   - 问题：PRD 枚举为 `已全部成功`，用例标题使用不存在枚举。
   - 根因：同义改写破坏了枚举精确性。

## UI/UX 主链路判断

本轮没有重启 API / 前端做新的浏览器截图验证，因为当前 API `127.0.0.1:8000` 和前端 `3000/5173` 均未响应；Postgres/Redis/Minio 仍在运行。UI 结论来自：此前页面巡检、前端规范、真实批次落库结果和 `.audit` 结构。

可给出的 UI/UX 结论：

- 上传/生成链路至少已经支持真实批次产出，说明 UI 改造没有阻断核心生成主流程。
- 模块树审查包已按业务模块输出，说明前端树展示方向与“模块 -> 分支 -> 用例”工作流一致。
- 但最新批次状态仍为 `pending_review`，全部用例 `review_status=pending`，所以 UI 分支不能把这批描述成“已完成用例资产”。
- 用例资产页/批次页必须继续强调三类状态：主集候选、待规格澄清、需修复。行业最佳实践上，测试管理工具应把“可执行测试”“需求问题”“生成错误/冲突”分流，不应混在一个默认列表里让 QA 自己猜。

## 行业最佳实践对齐

对齐项：

- **需求可追溯**：每条用例保留 `source_ref` / `verdict` / `bucket` / `verification.rationale`，符合 traceability 思路。
- **风险分层**：`P0/P1/P2`、`main/needs_spec/to_fix` 能帮助 QA 优先处理。
- **模块化测试资产**：顶层按业务模块、下层按分支组织，符合大型 PRD 的测试资产管理方式。
- **候选与债务分离**：已有 bucket 语义，为后续 UI 分流提供基础。

未完全对齐项：

- **可执行测试与需求澄清未充分分流**：`needs_spec` 仍以“用例”形式大量存在，行业上更适合作为 requirement question / spec debt / review finding。
- **枚举和值域应严格原文锁定**：状态枚举、接口字段、文案类断言不应同义改写。
- **性能/安全/接口类断言需要证据等级**：没有 PRD 或技术方案时，不能用 P0 确定测试标题表达。
- **审查包应自带报告**：当前需要人工从 `index.json` 汇总，不利于复盘和团队协作。

## 根因分析

1. **生成侧仍把“待确认问题”与“可执行用例”放在同一产物体系里**
   - `needs_spec=632` 说明 guard 能识别问题，但最终产物仍显得像一条普通测试用例。

2. **PRD 章节冲突没有上升为结构化澄清包**
   - `prd_conflict=35` 和 `verify_uncertain=66` 需要进入产品裁决，而不是靠 QA 在用例表逐条发现。

3. **模块树规则已改善，但兜底路径还不够产品化**
   - 44 条 `_review_required/unresolved_module` 说明还有一部分用例无法进入模块树，且其中多为 P0/P1。

4. **cap=4 控住了膨胀，但不能替代质量分流**
   - 每测试点最大 4 条已生效，但重复/待澄清/冲突仍需要独立策略处理。

## 建议顺序

1. **先不要再盲目跑更大批次**
   - 当前证据已经足够说明主流程跑通，但质量债务仍在。继续跑只会重复暴露同类问题。

2. **生成侧新开任务：把 `needs_spec` 从“用例”分流为“规格澄清项”**
   - 标题含 `【需求待确认】` 或 `verdict in (undefined, ungrounded)` 且 `bucket=needs_spec` 的条目，不应进入默认主集。
   - UI 可以展示为“待澄清”，但导出/主集默认不应混入。

3. **生成侧新开任务：枚举/文案/接口字段严格原文锁定**
   - 状态枚举、按钮文案、接口路径、请求体字段必须来自 PRD/技术方案证据。
   - 没证据时产出澄清问题，不产确定测试标题。

4. **UI 分支合并前补一个真实浏览器验收**
   - API + 前端启动后，打开 `/review`、最新 `/batches/5ad9...`、`/case-library`、`/exports`。
   - 验证：模块树默认浅展开/可收起、待澄清/需修复可见、主集候选不被误叫“已确认资产”、导出只选可见批次。
