# UI 重启后无 LLM 页面巡检自审

## 结论

本轮巡检有价值，但证据边界很窄。它证明重启后本地服务和核心页面入口能打开，不能证明真实生成质量、真实上传链路或首次使用平台 QA 的理解成本。

## 批判性问题

### 1. 是否更接近 QA 工程师真实工作流

部分接近。巡检覆盖了工作台、项目/系统、知识库、批次工作台、用例资产、全局搜索和导出中心，路径符合 QA 日常自动化测试资产流转。

但本轮没有让人按目标完成任务，也没有实际上传和生成，所以只能说页面入口可用，不能说动线已被真人证明清晰。

### 2. 是否误伤完整生成测试用例主流程

没有证据显示误伤。`src/testcase_generator/**` 无 diff，巡检期间未上传、未触发生成、未发起迭代、未落库归档、未导出新任务。

但这也意味着本轮没有覆盖 worker 真实执行生成 pipeline 的行为。生成主流程是否能跑通仍必须等公司 LLM 网关可用后验证。

### 3. 是否有遗漏

有。没有测试上传弹窗里的文档类型选择，因为这会创建真实文档；没有测试生成按钮，因为会触发 LLM；没有点击确认、需修改、删除、落库归档等 mutation。

这是有意限制，不是遗漏执行。当前阶段的目标是降低周一环境和页面入口风险，不是提前替代真实验收。

### 4. 是否发现新的业务风险

发现一个容易误判的风险：历史漫剧 PRD 仍是 `其他` 类型。后续验收必须用新上传 PRD 验证文档类型链路，不能拿旧数据作为新链路失败证据。

### 5. 是否可以合 main

不可以。GO 条件仍缺三项硬证据：

- 当前 HEAD 新小规模真实批次。
- 具备 QA 背景但首次使用平台的人的任务演练。
- 新批次 `.audit/<batch_id>/` 用例质量和模块树审查。

## 判定

本轮可以收口为“无 LLM 页面巡检证据”。提交后应再次运行不带 `--allow-dirty` 的完整预检，确保真实验收前置条件恢复为干净状态。
