# 验收脚本自审

## 结论

这套验收脚本方向正确：它没有继续盲目堆 UI 微调，而是补 UI/UX 分支当前最缺的证据，即真实新批次和首次使用平台的 QA 任务演练。

## 自审问题 1：是否把大 PRD 跑批误当成 UI 合并唯一门槛

没有。

大 PRD 跑一次好几个小时，主要验证生成质量、网关稳定性和大规模审查指标；UI/UX 分支没有改 `src/testcase_generator/**`，所以 UI 合并最小硬门槛应该是小规模真实批次能走通主链路。

脚本中保留完整大 PRD 批次，但把它放在小批次之后，并要求先判断失败归因。

## 自审问题 2：是否偏离“具备 QA 背景但首次使用平台”的用户口径

没有。

首次上手脚本没有要求用户解释 QA 基础概念，也没有做教学式检查；它只观察 QA 是否能从页面自己判断下一步：上传资料、生成批次、审查、资产、搜索、导出。

## 自审问题 3：是否足以证明“可合 main”

它能证明 UI/UX 合并所需的关键证据，但不是自动合并按钮。

仍需要真实执行后才能判断：

- 是否存在 P0/P1 主流程断点。
- 公司 LLM 网关是否能跑通。
- 首次使用者是否真的卡住。
- 新 `.audit` 审查包是否显示用例质量没有明显倒退。

因此本任务产物是“验收方法”，不是“验收已通过”。

## 自审问题 4：是否影响主流程

不影响。

本任务只写 Trellis 文档，不改代码，不改配置，不跑批，不触发真实 mutation。

## 自审问题 5：是否给用户增加技术负担

可接受。

文档里需要命令，但它们是可复制的健康检查；真正业务步骤仍然用页面语言描述。跑完后的回填模板也避免要求用户理解数据库或接口细节，只需要提供 batch id、页面现象和几个检查结果。

## 后续风险

- 如果小规模 PRD 选得太简单，可能证明不了复杂模块树和澄清链路。
- 如果完整大 PRD 失败，仍需单独定位是 UI、LLM 网关、还是 testcase generator 策略。
- 如果首次上手参与者已经看过平台演示，结果会偏乐观；最好找真正没用过当前 UI 的 QA。

## 最终判断

可以提交并归档本准备任务。下一次真正推进目标，应该在公司网络可用时按 `acceptance-runbook.md` 跑小规模真实批次；跑完后用 `post-batch-report-template.md` 回填，再继续 `.audit` 用例质量审查。
